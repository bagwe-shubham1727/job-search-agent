## 2. Turning "US-only" from prose into a hand-checkable rule (`BUILD_LOG.md`, Oct 29 18:10–19:19 ET; commits `053fda0`, `c1bd530`, `7aa5d0f`)
My first contract draft had several holes that Claude's review flagged: a baseline definition that conflicted with "first run reports none as new," no strict validator for Claude's JSON output, a 3-label model scale (`RELEVANT` / `PARTIAL` / `NOT_RELEVANT`) that could not be compared directly against 2-label hand labels (`MATCH` / `NO_MATCH`), punctuation stripping that turned `C#` into `c`, plain-English false positives on `react`, `express`, and `rest`, and escaped HTML in Greenhouse's `content`.

After fixing those and pulling hand-check candidates from the October 29 Stripe snapshot (`evidence/handcheck/stripe-jobs-2026-10-29T22-41-31Z.json`, 734 postings), I saw that posting `7543868` in Bengaluru, India passed both the title and skill checks. I decided to add a hard US-only location gate. However, my first phrasing ("clearly names a US city") was not hand-predictable across Stripe's 294 distinct `location.name` values, which included strings like `SF, NYC, CHI, ATL, SEA`, `SEA, SF, NY, Toronto`, `Toronto, CA` (where `, CA` looks like California), and `N/A`. At my direction ("keep the us only rule and add hand checks"), Claude compiled the 294 location strings into finite US and non-US signal lists (§6.4), where mixed US/non-US strings (`SEA, SF, NY, Toronto`) and bare `N/A` become `NOT_ESTABLISHED` (`NO_MATCH`), and found `8127182` (only `Java` matches) as my fewer-than-two-skills hand-check case (`CONTRACT.md §13` Case 4).

## 3. Subscription-only headless calls, worktree seams, and review fixes (`BUILD_LOG.md`, Oct 29 17:50 & 22:00 ET, Oct 30 02:05–03:10 ET)
Running `claude -p` under a Claude subscription (without an API key) hit three practical snags:
- A default `claude -p` call cost `$0.17` because it loaded local plugins, hooks, and `CLAUDE.md` files, while `--bare` failed with `"Not logged in"` because bare mode requires an API key. Running from a fresh empty directory under `data/tmp/` with `--setting-sources project --safe-mode --no-session-persistence --tools ""` (Plan Amendment `R1`, commit `33ea56e`) brought each call down to `~$0.008–$0.025` and ~1.6k–1.9k context tokens.
- When four coding agents (`WS1`–`WS4`) built the modules in parallel git worktrees, `WS3`'s CLI and `WS4`'s judge used guessed function signatures that would have crashed with a `TypeError` on the first `jsa run` that invoked the judge (`BUILD_LOG.md` 22:00 ET). An integration pass (commit `f2f3565`) reconciled the interfaces, deleted duplicate `SubprocessRunner` / `JSONPath` / skill-extractor implementations, and fixed a test failure where `test_no_count_constant` caught the substring `"734"` inside a hardcoded SHA-256 hash.
- The subsequent Google-style review (`02:05 ET`) and ponytail audit (`02:45 ET`, commits `b647a82..d53dabe` and `b3f3d30..7188965`) caught two deeper safety gaps: the child environment was a denylist that failed open (fixed in `R9` by switching `child_env` to an explicit allowlist of safe OS variables), and Claude's free-text `summary` / `reason` fields could echo sensitive résumé bullets into output records (fixed in `R10` with the `RESUME_VALUE_ECHO` validator rejection code).

## 4. What the three experiments taught me about rules vs. model judgment (`BUILD_LOG.md`, Oct 30–31; commits `7545af9`, `14e51f9`, `c2e5599`, `ed2c64c`, `8fea85b`)
- **Pre-registration and ordering gates (`BUILD_LOG.md` 02:35 ET):** Claude paused before running Chapter 1 sampling until I wrote my pre-run prediction and confirmed `experiments/sampling/hand_labels.json` (`f5fb431`), and paused again in Chapter 2 before freezing `judge.v2.md` (`c2e5599`) when my first draft included examples from held-out postings—replacing them with the full `CONTRACT.md §6` lists so the held-out set stayed clean.
- **Repeatability vs. correctness and the two-judge tradeoff:** In Chapter 1 (`7545af9`), `8249901` (`Software Engineer`, `Seattle, WA`) was `4/4` `NOT_RELEVANT` (`0/4` agreement with my `MATCH` hand label) because `judge.v1` penalized its 3-year experience and tier-0 infrastructure requirements, while `8127182` (`4/4` `NOT_RELEVANT`) and `8234357` (`3 × NOT_RELEVANT`, `1 × RELEVANT`) agreed with `NO_MATCH` only because of experience requirements (`5–12+` and `2–5+` years) rather than the $<2$-skill or `"N/A"`-location gates they actually failed. In Chapter 2 (`14e51f9` $\to$ `ed2c64c`), replacing `label_definition` with the four-gate rule in `judge.v2.md` raised agreement from `7/10` to `10/10` on `dev` and from `6/10` to `10/10` on `heldout`. Yet that `10/10` result also showed that spelling out the deterministic rule in the prompt turns Claude into an expensive copy of the Python rule instead of an independent second opinion—whereas `v1` flagging `5+` year and Mandarin-fluency roles as a bad fit for a new-grad persona was actually useful signal.
- **Why the model shouldn't own I/O (`8fea85b`):** In Chapter 3 surface `(c)`, letting Claude fetch the board via `WebFetch` and edit `state.json` took 5 chunked fetches (`$0.1311` vs. `$0.0234` in `(a)`), passed the JSON through a summarizing model that cut off one posting mid-entry so its ID was invisible, and forced the model to diff 700+ IDs "by eye." Keeping network fetch, SHA-256 logging, and atomic state updates in Python while giving the model `--tools ""` (surface `(a)`) is both cheaper and safer.
